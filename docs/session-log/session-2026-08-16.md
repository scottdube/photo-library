## Summary

Closed out next step #1 from session 2026-04-27, 109 days late. The pre-migration Photos library copy at `~/Pictures/Photos Library.photoslibrary` (116 GiB) was still on the Mac Mini's internal disk and was the cause of disk-space pressure. Before deleting it, verified it held no unique content: 113 original files exist on the internal copy but not on the external, resolving to 73 distinct assets, **all of which are confirmed non-live** — content deleted from Photos after the migration. External library health re-verified at 0 missing against the Phase 0 filter set, identical to the 2026-04-27 baseline. Internal copy moved to Trash.

## Setup

**Live library:** `/Volumes/4TB_Removable/Photos/Photos Library.photoslibrary` — System Photo Library since 2026-04-27, iCloud set to "Download Originals to this Mac."

**Stale copy under evaluation:** `~/Pictures/Photos Library.photoslibrary`, 116 GiB (`du -sh`), which reconciles exactly to the 124,472,910,792 bytes recorded at migration (124,472,910,792 / 1024³ = 115.9 GiB). Bundle unchanged in size since 2026-04-27.

## Methodology

The initial approach — infer liveness from bundle modification times — proved unreliable and was abandoned. See Key findings. The verification that actually settled the question:

1. Compared bundle and inner-database timestamps on both libraries.
2. Counted open file handles held by `photolibraryd` / `photoanalysisd` against each library.
3. Compared `originals/` basenames between the two libraries. Basenames are asset UUIDs, so the set difference is the set of assets present on internal but absent on external.
4. Reduced the 113 differing filenames to 73 distinct UUIDs (stripping `_3` Live Photo motion suffixes and extensions).
5. Swept the entire external bundle once for any trace of those 73 UUIDs — files or directories, including `resources/derivatives/`.
6. Queried the external library's database via `osxphotos query --uuid` for every UUID that left a trace, to distinguish live assets from orphaned derivatives.
7. Re-ran the 2026-04-27 health queries against the external library to confirm no regression.
8. Moved the internal copy to `~/.Trash/` after quitting Photos.

## Key findings

**Bundle mtime is not a reliable liveness signal for a `.photoslibrary`.** The internal bundle's directory mtime read Apr 27 while `database/Photos.sqlite` inside it was written Jul 7. Directory mtimes change only when entries are added or removed at that level, so in-place writes to files inside the bundle are invisible at the top. Any future "is this library still in use" question must inspect the inner database, not the bundle.

**The set-difference-then-UUID-liveness check is the right verification.** It answers the actual question — "does the copy I am about to delete hold anything the live library does not" — without depending on activity signals, timestamps, or assumptions about which process has what open. It should be the standard procedure before deleting any library copy.

**All 73 orphans are deleted content, and the video subset is explained.** The stills left no trace anywhere on the external, consistent with deletion after 2026-04-27 followed by Recently Deleted purge. The 7 videos left derivative directories but no database entry, which is the expected residue of a deleted video asset — Photos purges the original and the DB row before it reclaims the converted-video derivative.

**Unfiltered `--missing` counts are not comparable to the project baseline.** The unfiltered 4,143 initially read as a severe regression from the 2026-04-27 figure of 0. It is not: the baseline was measured with `--only-photos --not-hidden --not-shared`, and the unfiltered count includes Shared Album assets, which have no local original by design, plus hidden items and videos. Matched to the original filter, the count is 0. Always reproduce the filter before comparing.

**Not photo-frame.** The Jul 7 write was checked against the photo-frame project's known video re-download bug and ruled out: that ingest path hits iCloud's webstream API directly and never reads the local Photos library. See `photo-frame` project notes.

## Known issues

**Internal `Photos.sqlite` written 2026-07-07 16:27 — cause unknown.** Ten weeks after the migration, something wrote to the stale library's database. Candidates, none verified: a one-off Option-launch into the old library; an OS update touching it; a tool run against `PHOTOS_LIBRARY_PATH` from `.env.example`, which still pointed at the internal path until this session. Not pursued because the content comparison made it moot.

**26 open file handles on the stale library — cause unknown.** `photolibraryd` / `photoanalysisd` held handles on the internal library while the external was demonstrably the active one. Possibly related to the Jul 7 write. Revisit only if Photos misbehaves post-deletion.

**The 4,143 unfiltered missing assets have not been decomposed.** Expected to be dominated by Shared Albums, but `--shared --missing --count` and `--only-movies --missing --count` were not run. This decomposition decides Phase 1's filter posture and is carried forward.

**Trash not emptied.** The internal copy is in `~/.Trash/`; disk space is not reclaimed until it is emptied, and possibly not until APFS local snapshots age out.

## Decisions

**[DECISION] Delete the internal library copy.** Justified by content comparison, not by activity signals: 113 differing files, 73 assets, 0 live. Retention past the original 24–48 hour window produced no benefit and cost 116 GiB.

**[DECISION] Set-difference-plus-UUID-liveness is the standard pre-deletion check** for any Photos library copy, superseding timestamp inspection. Recorded in project memory as a reusable procedure.

**[DECISION] `.env.example` repointed to the external volume.** `PHOTOS_LIBRARY_PATH` now targets `/Volumes/4TB_Removable/Photos/Photos Library.photoslibrary`; `INDEX_DB_PATH` and `THUMBNAIL_CACHE_DIR` move from `~/photo-library-data/` on the internal disk to `/Volumes/4TB_Removable/photo-library/`, matching the 2026-04-27 decision reserving that path for Phase 1 artifacts. Left as-is, Phase 1 would have written a multi-GB index back onto the disk this session cleared.

**[DECISION] No orphan-rescue copy taken.** The 113 files are content deliberately deleted from Photos. Copying them to the external was offered and declined as unnecessary.
